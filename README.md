# openspec-config

Share one OpenSpec [`openspec/config.yaml`](https://openspec.dev/docs/configuration/config-yaml) across multiple repos — updated like a dependency, not by hand.

OpenSpec keeps each repo's config in `openspec/config.yaml`, with no built-in way to keep those files consistent across projects. This package ships a shared **base config** plus a small CLI that regenerates each repo's `config.yaml` from it. Because the base arrives as an npm dependency, its version is pinned in your lockfile and updates flow in as ordinary dependency-bump PRs.

## Consumer setup

In a repo that uses OpenSpec (needs a `package.json` — run `npm init -y` first if there isn't one):

```bash
npm install --save-dev openspec-config

# adopt (first time only; --force replaces the existing config,
# so fold any hand edits into the override file first)
npx openspec-config sync --force
```

This writes `openspec/config.yaml` with a generated header:

```yaml
# Generated by openspec-config@1.0.0. Do not edit by hand.
# Source: https://github.com/davegoopot/openspec-config — rerun `openspec-config sync` to update.
schema: spec-driven
```

Commit the generated file, and treat it exactly like a lockfile: never hand-edit it.

## Commands

| Command | What it does |
|---|---|
| `openspec-config sync` | Regenerate `openspec/config.yaml` from the base + override |
| `openspec-config check` | Exit 0 if the file matches what `sync` would produce, 1 + diff otherwise (CI mode) |

Options: `--dir <path>` (target project root, default `.`), `--force` (overwrite a config lacking the generated header — use once when adopting), `--base <path>` (install an alternative base, advanced).

`sync` refuses to overwrite a `config.yaml` that wasn't generated by this tool, so it can't silently destroy a hand-written config.

## Per-repo overrides

Repos can add their own keys on top of the base in `openspec/config.override.yaml` (committed like any other file):

```yaml
# openspec/config.override.yaml
store: team-plans        # e.g. this repo plans in an OpenSpec store

rules:
  proposal:              # replaces the base's rules.proposal list wholesale
    - Keep proposals under 500 words
    - Always state what is out of scope
```

Merge semantics, kept deliberately simple:

- nested **maps deep-merge**
- **scalars and arrays replace** the base value at the deepest key provided
- setting a key to `null` **deletes** it from the base

Override anything OpenSpec supports (`store`, `references`, `context`, `rules`, `operations`, …).

## Keeping configs consistent (CI)

Add this workflow to each consumer repo. Regular PRs get a drift check; Dependabot bump PRs get the config regenerated and committed back to the branch, so the PR shows the real config diff:

```yaml
# .github/workflows/openspec-config.yml
name: openspec-config
on:
  pull_request:
jobs:
  openspec:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.head_ref }}
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - name: Self-heal Dependabot bump PRs
        if: github.actor == 'dependabot[bot]'
        run: |
          npx openspec-config sync
          git config user.name "openspec-config[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git add openspec/config.yaml
          git diff --cached --quiet || (git commit -m "chore: regenerate openspec/config.yaml" && git push)
      - name: Check (human PRs)
        if: github.actor != 'dependabot[bot]'
        run: npx openspec-config check
```

And let Dependabot watch the package:

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: "/"
    schedule:
      interval: weekly
    allow:
      - dependency-name: "openspec-config"
```

## Changing the shared base

1. Open a PR against [`config/base.yaml`](config/base.yaml) in this repo. Comments there are maintainer documentation only — they don't propagate to generated files, so put real content in actual values.
2. Merge, then version and publish:

```bash
npm version minor        # or major/patch — see policy below
npm publish
```

3. Dependabot opens bump PRs in the consumer repos; merge them to roll the new base out.

**Semver policy:** changes that add rules are `minor`; changes that alter or remove behavior (editing existing rules, changing `context`, removing keys) are `major`. Use this license — the diff in each consumer PR is exactly what the agent's behavior change will be.

Keep the base short: everything in it lands in every agent prompt on every run ([OpenSpec's advice](https://openspec.dev/docs/project-config)).

## Development

```bash
npm install
npm test        # unit + end-to-end CLI tests
```

`config/base.yaml` is the shared source of truth; `lib/core.mjs` holds the merge, emit, and diff logic; `bin/cli.mjs` is the thin CLI entry.
